MVP Codex Skill Specs

This artifact defines the first useful set of Codex skills for Agile Blueprinting / Blueprint to Release.

The goal is not to operationalize the full methodology at once. The goal is to create a minimal, useful workflow that helps teams generate better PRDs, assess readiness before build, implement code, and produce test evidence.

MVP Skill Set

Skill Plugin Bundle Primary User Primary Output
prd-generator Product plugin Product / BA PRD / blueprint artifact
prd-readiness-review Product plugin, shared with Engineering Product / Engineering Readiness review with gaps, risks, and recommendation
implementation-agent Engineering plugin Engineering Code changes plus implementation artifact
unit-test-agent Engineering plugin Engineering / QA Unit test changes plus test evidence
e2e-test-agent Engineering plugin Engineering / QA E2E test plan/results plus test evidence

Shared Skill Behavior

Every MVP skill should:

  • Use plain-language guided prompts.
  • Keep the user from needing to remember the full methodology.
  • Write predictable Markdown artifacts.
  • Distinguish facts, assumptions, risks, open questions, and deviations.
  • Make HITL review points visible without making the user manage the full governance model manually.
  • Prefer progress over ceremony while preserving enough structure to reduce rework.

Unless otherwise specified, MVP generated artifacts should be Markdown first. Structured YAML frontmatter may be included where needed for future SPOG/artifact review compatibility.

Skill: prd-generator

Plugin bundle:

  • Product plugin

Purpose:

Guide Product, Design, or BA-style users through the creation of a PRD/blueprint without requiring them to know the PRD structure in advance.

Primary outcome:

  • A PRD/blueprint artifact that is clear enough for Product review, customer/proxy direction review, and Engineering readiness review.

Inputs:

  • Capability name
  • Work item or ticket ID, if available
  • Customer/requester context
  • Problem statement
  • Desired outcome
  • Discovery notes, if available
  • Workflow notes, sketches, wireframes, screenshots, or examples, if available
  • Known constraints, assumptions, dependencies, and risks

Guided interview areas:

  1. What problem are we solving?
  2. Who is affected?
  3. What should be true when this ships?
  4. What is in scope?
  5. What is explicitly out of scope?
  6. What is the end-to-end workflow?
  7. What alternate, error, or exception flows matter?
  8. What data, entities, fields, state changes, or database records are involved?
  9. What business rules and validations apply?
  10. What screens, surfaces, states, and accessibility expectations matter?
  11. What integrations or external systems are involved?
  12. What security, privacy, logging, audit, reliability, or performance expectations apply?
  13. What acceptance criteria prove the work is done?
  14. What tests should exist?
  15. What open questions remain?

Expected output:

  • PRD/blueprint Markdown document using PRD-TEMPLATE.md as the source structure.
  • Open questions section.
  • Assumptions section.
  • Readiness checklist with checked, unchecked, or unknown items.
  • Recommendation: ready_for_review, needs_discovery, or not_ready.

Success criteria:

  • The user can produce a credible first PRD without knowing the template.
  • Missing answers are captured as open questions rather than silently ignored.
  • The PRD is detailed enough for prd-readiness-review to evaluate.

Failure / stop conditions:

  • The user cannot identify the problem or desired outcome.
  • Scope is too unclear to distinguish in-scope from out-of-scope.
  • The request is actually an amendment, support task, defect, or operational task and should be routed elsewhere.

Skill: prd-readiness-review

Plugin bundle:

  • Product plugin initially
  • Shared with Engineering for review/approval support

Purpose:

Assess whether a PRD/blueprint is actionable enough for Engineering or Codex-assisted implementation.

Primary outcome:

  • A readiness review that identifies whether the PRD is ready for agent handoff, needs revision, needs customer clarification, or should be re-scoped.

Inputs:

  • PRD/blueprint artifact
  • Discovery notes, if available
  • Customer/proxy direction evidence, if available
  • Applicable HITL checkpoint expectations
  • Amendment/re-scope trigger rules

Review areas:

  1. Outcome and problem clarity
  2. Scope boundaries
  3. Workflow completeness
  4. Alternate and exception flows
  5. Data, state, validation, and business rules
  6. UX surfaces and states
  7. Integrations and dependencies
  8. Security, privacy, logging, and audit expectations
  9. Acceptance criteria quality
  10. Testability
  11. Assumptions and open questions
  12. Amendment/re-scope risk

Expected output:

  • Readiness review Markdown artifact.
  • Summary recommendation:
    • ready_for_agent_handoff
    • ready_with_assumptions
    • needs_revision
    • needs_customer_clarification
    • re_scope_recommended
  • Gap list grouped by severity.
  • Suggested clarifying questions.
  • Engineering concerns, if any.
  • HITL note identifying who needs to review next.

Success criteria:

  • Engineering can tell quickly whether implementation can begin.
  • Product gets specific, actionable revision guidance.
  • The review prevents implementation from becoming the first discovery of PRD gaps.

Failure / stop conditions:

  • PRD is missing entirely.
  • PRD contradicts itself.
  • Acceptance criteria are absent or untestable.
  • Required customer/proxy direction is missing for a customer-facing change.

Skill: implementation-agent

Plugin bundle:

  • Engineering plugin

Purpose:

Implement the approved PRD/blueprint in the target codebase and produce evidence that maps implementation work back to the PRD.

Primary outcome:

  • Code changes, branch/PR-ready implementation, and an implementation artifact.

Inputs:

  • Approved PRD/blueprint
  • Readiness review, if available
  • Repository path
  • Branch/PR expectations
  • Existing codebase conventions
  • Build/run/test commands, if known
  • Amendment/re-scope rules

Guided prompts:

  1. What repo should be used?
  2. What branch or worktree should be used?
  3. What PRD/blueprint should govern the work?
  4. What build/test commands are expected?
  5. Are there files, modules, or components likely to be in scope?
  6. Are there implementation constraints, coding standards, or forbidden approaches?
  7. Should a PR be opened, or should the output remain local/PR-ready?

Expected behavior:

  • Read the codebase before editing.
  • Follow existing patterns.
  • Implement only the approved scope.
  • Identify any material scope or behavior change that may require amendment/re-scope review.
  • Add or update tests when appropriate.
  • Produce an implementation artifact compatible with 02-implementation.md.

Expected output:

  • Code changes.
  • Build/run notes.
  • Files changed summary.
  • PRD requirement mapping.
  • Tests added or updated.
  • Known deviations from PRD.
  • Risks and open questions.
  • Required human review note.

Success criteria:

  • Implementation maps clearly to approved PRD requirements.
  • Local build/test evidence exists when available.
  • Deviations, assumptions, and risks are documented.
  • Work is ready for Engineering review or PR review.

Failure / stop conditions:

  • PRD is not approved or actionable enough.
  • Required repository context is unavailable.
  • Implementation would materially change scope without amendment/re-scope approval.
  • Build/test failures cannot be resolved or explained.

Skill: unit-test-agent

Plugin bundle:

  • Engineering plugin

Purpose:

Create, update, or run unit tests for the implemented capability and produce test evidence mapped to the PRD and implementation.

Primary outcome:

  • Unit test changes and a test evidence artifact.

Inputs:

  • PRD/blueprint
  • Implementation artifact or branch
  • Repository path
  • Existing test conventions
  • Unit test command, if known
  • Acceptance criteria

Guided prompts:

  1. What repo/branch should be tested?
  2. What PRD/acceptance criteria should tests map to?
  3. What unit test command should be used?
  4. Are there specific components, services, functions, or rules that require coverage?
  5. Should the skill add missing tests, run existing tests, or both?

Expected behavior:

  • Inspect existing unit test patterns.
  • Add or update focused unit tests for business rules, edge cases, validations, and component logic.
  • Run unit tests when possible.
  • Report pass/fail/pending clearly.
  • Avoid claiming coverage that does not exist.

Expected output:

  • Unit tests added or updated.
  • Unit test command/results.
  • Acceptance criteria mapping.
  • Coverage notes.
  • Failed tests and likely causes.
  • Gaps or recommended follow-up.

Success criteria:

  • Unit tests exercise meaningful implementation behavior.
  • Results are reproducible or clearly documented.
  • Gaps are visible before PR/merge review.

Failure / stop conditions:

  • Test environment cannot run.
  • Existing test framework is missing or unclear.
  • Implementation is unavailable.
  • Tests reveal a blocking defect.

Skill: e2e-test-agent

Plugin bundle:

  • Engineering plugin

Purpose:

Create, update, run, or recommend end-to-end tests that validate the implemented user/system workflow against PRD acceptance criteria.

Primary outcome:

  • E2E test plan/results and evidence mapped to the PRD.

Inputs:

  • PRD/blueprint
  • Implementation artifact or branch
  • Repository path
  • App run instructions
  • E2E test framework and command, if known
  • Test data and environment details
  • Acceptance criteria

Guided prompts:

  1. What workflow needs E2E validation?
  2. What app/environment should be used?
  3. What command starts the app?
  4. What command runs E2E tests?
  5. What test data, accounts, roles, or permissions are needed?
  6. Which acceptance criteria are must-cover for MVP?
  7. Should the skill add missing E2E tests, run existing tests, or both?

Expected behavior:

  • Identify the critical user/system path.
  • Map E2E coverage to acceptance criteria.
  • Add or update E2E tests where practical.
  • Run tests when the environment is available.
  • Capture screenshots, logs, traces, or other evidence where useful.
  • Mark environment or data blockers explicitly.

Expected output:

  • E2E test plan.
  • E2E tests added or updated, if applicable.
  • Test command/results.
  • Acceptance criteria mapping.
  • Evidence paths, screenshots, logs, or traces.
  • Environment/test data notes.
  • Failed tests and blocking issues.
  • Recommended follow-up.

Success criteria:

  • Critical workflow is validated or clearly blocked.
  • Acceptance coverage is visible.
  • The result is usable by QA and Engineering review.

Failure / stop conditions:

  • App cannot run.
  • E2E environment is unavailable.
  • Required credentials/test data are unavailable.
  • E2E tests reveal a blocking workflow failure.

MVP Rollout Notes

These five skills are enough to prove the operating model without introducing the entire Blueprint to Release process.

Recommended first rollout sequence:

  1. prd-generator
  2. prd-readiness-review
  3. implementation-agent
  4. unit-test-agent
  5. e2e-test-agent

The rollout should not require the full HITL matrix, SPOG, packaging, deployment, communications, security, or amendment flow on day one. Those can be layered in after the first skills prove useful and teams begin building consistent habits.
