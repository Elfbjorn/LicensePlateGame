Agent Artifact Contract

This document defines the feeder contract for the Single Pane of Glass (SPOG). Each agent produces a structured artifact in a common run directory. The SPOG artifact review agent reads that directory, validates expected files, summarizes each agent output into a KPI, and distinguishes missing artifacts from failed artifacts.

Initial assumption: all standard agents are expected to run for every Blueprint to Release execution. In reality, some agents may be not applicable for a given platform or delivery lane, but the first version of the process assumes a consistent agent set so the SPOG always has the same KPIs in the same place.

Goals

  • Make every agent output machine-readable and human-reviewable.
  • Keep common YAML frontmatter consistent across all artifacts.
  • Allow each agent to tune the body of its report to its job.
  • Store all artifacts for a run in a single identifiable folder.
  • Make missing artifacts visible as missing, not as failed.
  • Include HITL review metadata with each agent artifact.
  • Allow the SPOG agent to generate consistent KPI cards from consistent inputs.

Artifact Directory

Recommended directory name:

artifacts/

Recommended run folder format:

artifacts/<work-item-id>/

Examples:

artifacts/JIRA-1234/
artifacts/BUG-2026-0042/
artifacts/REQ-2026-0117/

Alternative if no work item ID exists:

artifacts/<YYYY-MM-DD>-<short-slug>/

Examples:

artifacts/2026-06-04-intake-page-validation/
artifacts/2026-06-04-salesforce-contact-sync/

Preferred rule:

Use a stable work item ID when available. Use a date-stamped slug only when no ticket/request ID exists. The folder must uniquely identify this run so artifacts from prior work are never overwritten or confused with current evidence.

Expected Files

Each run folder should contain the same expected files:

artifacts/<work-item-id>/
  00-run-metadata.md
  01-prd-blueprint.md
  02-implementation.md
  03-quality-test.md
  04-security.md
  05-documentation-comms.md
  06-packaging.md
  07-deployment-helm.md
  08-artifact-review.md
  09-spog.md

Notes:

  • 09-spog.md is generated by the artifact review agent after reading the other artifacts.
  • If an agent is not applicable, it should still produce its expected file with status: not_applicable and an explanation.
  • If an expected file is missing, SPOG should show that KPI as missing.
  • missing is distinct from failed. Missing means no artifact was found. Failed means an artifact exists and reports failure.

Common Field Definitions

Field Required Description
artifact_schema_version Yes Version of this artifact contract.
artifact_type Yes Type of artifact, such as implementation, quality_test, security, packaging, deployment_helm, artifact_review, or spog.
work_item_id Yes Ticket/request identifier when available.
run_id Yes Identifier for this specific Blueprint to Release run. Usually same as work item ID.
run_folder Yes Relative path to the artifact folder.
capability_name Yes Name of the capability or release.
agent_name Yes Agent that produced the artifact.
agent_version No Agent version or prompt version if available.
agent_run_id No Execution ID, job ID, or trace ID if available.
created_at Yes Timestamp when artifact was created.
tested_at Conditional Timestamp when validation was performed. Required for QA, security, packaging, and deployment artifacts.
status Yes pass, warning, fail, not_applicable, missing, or pending.
status_reason Yes Short explanation of the status.
summary Yes One- to three-sentence summary for SPOG display.
prd_reference Yes Link/path to the PRD artifact.
source_inputs Yes Inputs the agent relied on.
evidence Yes Links/paths to supporting evidence.
risks Yes Risks identified by the agent. Use empty list if none.
open_questions Yes Questions needing human or customer input. Use empty list if none.
deviations_from_prd Yes Places where the work deviates from the PRD. Use empty list if none.
requires_human_review Yes Usually true.
hitl_review Yes Human review metadata for this artifact.

Status Values

Status Meaning SPOG KPI
pass Agent completed work and found no blocking concerns Green
warning Agent completed work but identified non-blocking concerns or accepted risk Yellow
fail Agent completed work and found blocking concerns Red
not_applicable Agent produced an artifact explaining why the work does not apply Gray
missing Expected artifact file was not found Missing / distinct from Red
pending Artifact exists but is waiting for work or review Blue

SPOG rule:

Do not infer not_applicable from a missing file. If the file is absent, the KPI is missing. If the agent is not needed, it must say so in its own artifact.

HITL Review Values

hitl_review.decision values:

  • pending
  • approved
  • rejected
  • approved_with_risk
  • needs_revision
  • re_scope

hitl_review.agrees_with_agent values:

  • pending
  • agree
  • disagree
  • partially_agree
  • not_applicable

hitl_review.recommendation values:

  • pending
  • ready_to_proceed
  • not_ready
  • proceed_with_risk
  • needs_revision
  • re_scope

Agent-Specific Body Requirements

The YAML frontmatter is consistent across all artifacts. The Markdown body should be tuned to the agent's job.

00-run-metadata.md

Purpose: Define the run and expected artifact set.

Required body sections:

  • Work item summary
  • Intake classification
  • Delivery lane
  • Expected agents
  • Expected files
  • Required HITL reviewers
  • Links to PRD, ticket, repo, branch, and PR

01-prd-blueprint.md

Purpose: Store the approved PRD/blueprint or a pointer to it.

Required body sections:

  • PRD summary
  • Definition of Ready status
  • Product/BA sign-off
  • Customer/proxy sign-off
  • Assumptions
  • Open questions
  • Amendment policy

02-implementation.md

Purpose: Summarize code changes produced by the implementation agent.

Required body sections:

  • Implementation summary
  • Branch and PR links
  • Files changed
  • Components changed
  • Design decisions
  • PRD requirements implemented
  • Known deviations from PRD
  • Build/run notes

03-quality-test.md

Purpose: Summarize quality and automated test results.

Required body sections:

  • Test plan
  • Tests executed
  • Test results
  • Failed tests
  • Coverage notes
  • Acceptance criteria mapping
  • Regression risks
  • Recommended follow-up

04-security.md

Purpose: Summarize security checks and risks.

Required body sections:

  • Security checks performed
  • Sensitive data involved
  • Authentication/authorization review
  • Input validation review
  • Integration risks
  • Logging/audit review
  • Findings
  • Mitigations
  • Accepted risks

05-documentation-comms.md

Purpose: Summarize documentation and communications artifacts generated by the documentation/comms agent.

Required body sections:

  • Release notes summary
  • Customer-facing summary
  • Support notes
  • User/admin documentation
  • Known limitations
  • Audience map
  • Documentation gaps

Note: Communications planning will be defined separately later, but this artifact slot remains standard so SPOG always has the same KPI layout.

06-packaging.md

Purpose: Summarize packaging work, such as Docker images or other deployable artifacts.

Required body sections:

  • Packaging summary
  • Package/image details
  • Build commands or pipeline references
  • Runtime assumptions
  • Environment requirements
  • Version/tag information
  • Package validation results
  • Known package risks

07-deployment-helm.md

Purpose: Summarize deployment assets, including Helm charts when applicable.

Required body sections:

  • Deployment summary
  • Helm chart details, if applicable
  • Deployment configuration
  • Environment variables
  • Secrets checklist
  • Migration requirements
  • Rollback plan
  • Monitoring/alerting expectations
  • Deployment validation results

08-artifact-review.md

Purpose: Summarize whether the artifact set is complete and internally consistent.

Required body sections:

  • Expected artifact checklist
  • Missing artifacts
  • Artifact statuses
  • Cross-artifact conflicts
  • Open risks
  • Open questions
  • Deviations from PRD
  • SPOG generation readiness

09-spog.md

Purpose: Generate the Single Pane of Glass dashboard.

Required body sections:

  • Dashboard header
  • KPI summary
  • Drill-down details
  • HITL sign-off summary
  • Missing artifacts
  • Blocking risks
  • Ship/hold recommendation
  • Final release decision record

SPOG Artifact Review Logic

The artifact review agent should:

  1. Read 00-run-metadata.md.
  2. Determine the expected file list.
  3. Check whether each expected file exists.
  4. Parse YAML frontmatter from each existing artifact.
  5. Validate required fields.
  6. Map each artifact status to the SPOG KPI status.
  7. Mark any absent expected file as missing.
  8. Identify artifacts with pending HITL review.
  9. Identify disagreement between agent outcome and HITL recommendation.
  10. Identify cross-artifact conflicts.
  11. Generate 08-artifact-review.md.
  12. Generate 09-spog.md.

Missing vs Failed

Missing:

  • Expected file does not exist.
  • SPOG should display the KPI as missing.
  • This means the review cannot conclude whether that stage passed or failed.

Failed:

  • Expected file exists.
  • Agent reports status: fail.
  • SPOG should display the KPI as red.
  • This means the stage produced evidence of a blocking concern.

Not applicable:

  • Expected file exists.
  • Agent reports status: not_applicable.
  • Agent explains why the stage does not apply.
  • SPOG should display the KPI as gray.

Open Questions

  • Should the common directory be named artifacts, reviews, or something more specific?
  • Should run folders always use ticket IDs when available?
  • Should SPOG reject a run if any HITL review is still pending?
  • Should the artifact review agent be allowed to generate placeholder missing-artifact records, or should missing remain purely inferred?
  • Should agent artifacts be Markdown only, or Markdown plus JSON for machine parsing?
