Agent Evidence

The output an AI/Codex agent or skill produces to show what it did, what it reviewed, what it found, and what requires human attention.

Agent evidence may include summaries, files changed, test results, screenshots, logs, risks, open questions, deviations from the PRD, and recommended follow-up.

Agile Blueprinting

A delivery model for AI-assisted software work that combines waterfall's clarity, agile's cadence, and AI's delivery compression.

Agile Blueprinting starts with a clear blueprint of the whole deliverable before implementation begins. It keeps agile's feedback loops and human review points, but avoids fragmenting larger work into thin user stories that lack enough context for AI-assisted delivery.

Amendment

A course correction to approved work that remains connected to the same customer/business need and intended outcome.

Accepted amendments become part of the current release scope and should be captured as related linked tickets, not silent edits to the original requirement.

Artifact

A durable Markdown output created by the process.

Artifacts may be process references, PRDs, readiness reviews, implementation summaries, test evidence, HITL matrices, communication models, or skill specs. Mature artifacts become the source of truth for repeatable workflows.

Blueprint

The source-of-truth description of the deliverable.

A blueprint explains what is being built, why it matters, who it serves, how it should behave, what data and rules apply, what is in and out of scope, and how the result will be validated.

In this model, a PRD is the primary blueprint artifact.

Blueprint to Release

The operating flow for Agile Blueprinting.

Blueprint to Release describes how work moves from intake to categorization, discovery, PRD/blueprint creation, readiness review, implementation, testing, human approval, release, and closure.

Categorized

The preferred term for routing a ticket or request into a work type.

Use categorized, not classified, because classified has a different meaning in the operating environment.

Typical categories include defect, O&M / operational task, new request / feature / application, amendment / re-scope, and security / risk.

Codex Plugin

A team-facing bundle of related Codex skills.

The initial plugin model uses Product, Engineering, and Operations plugins. Each plugin contains the skills relevant to that team or operating role.

Codex Skill

A guided workflow that helps a user complete a specific job, such as generating a PRD, reviewing readiness, implementing code, or producing test evidence.

Skills should hide process complexity, ask useful questions, read relevant artifacts, and generate predictable outputs.

Customer Proxy

A person or group authorized to represent the customer for discovery, direction, sign-off, acceptance, or closure.

Product may coordinate customer communication, but Product is not automatically the customer proxy unless formally authorized for that decision.

Definition of Ready

The review standard for deciding whether a PRD/blueprint is ready for agent or Engineering handoff.

Definition of Ready asks whether the customer need, outcome, workflow, scope, data, rules, acceptance criteria, assumptions, open questions, and sign-offs are clear enough to govern delivery.

Delivery Lane

The operating path selected after a request is categorized.

Examples include Sprint / Planned Delivery, Kanban / O&M, Expedited / Security-Led, and Amendment / Re-Scope.

Done

The overall closure standard for a request or initiative.

Done means the work has reached the target environment, required reviews are complete, the requester or final approval owner confirms that what was delivered matches expectations, and supporting tickets are ready for closure.

Engineering Done

The point where Engineering has completed the work it owns and has no reason to believe more Engineering work is required before handoff.

Engineering Done can include implementation, tests, PR review, build/run notes, deployment handoff, risk notes, and tagging the next owner. Engineering Done does not mean the overall customer-facing request is closed.

Final Approval Owner

The person or group who made the request and confirms that what was delivered matches expectations.

If the customer made the request, the customer is the final approval owner. If Product made the request for Product's own need, Product is the final approval owner. Engineering does not become final approval owner merely because it delivered the implementation.

HITL

Human-in-the-loop.

HITL means humans make the important decisions at the right checkpoints. AI or Codex skills may generate work, evidence, recommendations, and summaries, but humans remain accountable for scope, readiness, risk acceptance, release, and final approval.

HITL Checkpoint

A human review point where an authorized person or group approves, rejects, requests revision, accepts risk, or redirects work.

Examples include PRD/blueprint review, Definition of Ready, implementation review, testing review, security/risk review, release decision, and closure approval.

New Request

A separate body of work created when a proposed change refutes the original understanding, is unrelated to the initial request, changes the intended business outcome, or introduces a materially different capability, workflow, audience, or system behavior.

New requests do not block the current release unless separately prioritized and approved.

PRD / Blueprint

The product requirements document used as the governing artifact for AI-assisted delivery.

It should be clear enough for Product, the customer or customer proxy, Engineering, QA, DevOps, and Codex skills/agents to understand the intended outcome and produce work against it.

PRD Generator

The MVP Product skill that guides a user through creating a PRD/blueprint.

Its job is to ask plain-language questions, generate the best available PRD, and preserve unknowns as assumptions or open questions.

PRD Readiness Review

The MVP review skill that evaluates whether a PRD/blueprint is actionable enough for Engineering or Codex-assisted implementation.

It identifies gaps, risks, open questions, and whether the PRD is ready for agent handoff, ready with assumptions, needs revision, needs customer clarification, or should be re-scoped.

Product Done

A Product-owned definition of done that should be finalized by Product/Design.

In broad terms, Product Done concerns discovery, PRD/blueprint quality, customer/proxy alignment, acceptance coordination, and follow-on or amendment handling. The exact definition is deferred until Product/Design owns and approves it.

Ready

A state where the PRD/blueprint is clear enough to move to the next stage with bounded risk.

Ready does not mean perfect. It means the known gaps, assumptions, scope, acceptance criteria, and risks are explicit enough that humans can decide whether work should proceed.

Re-Scope

A review path used when proposed changes materially affect scope, workflow, data, implementation effort, risk, or release expectations.

Engineering owns the final decision on whether a change requires amendment/re-scope review.

SPOG

Single Pane of Glass.

The SPOG is the final review dashboard for a Blueprint to Release run. It consolidates agent evidence, human review status, risks, open questions, and release readiness into one review surface.

Support / Operations Done

A Support/Ops-owned definition of done that should be finalized by Support/Operations.

In broad terms, Support/Ops Done concerns triage, customer updates, support-resolvable fixes, operational validation, escalation, and customer-facing closure communication. The exact definition is deferred until Support/Operations owns and approves it.
