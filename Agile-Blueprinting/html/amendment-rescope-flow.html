Amendment / Re-Scope Flow

This artifact defines when a change to an approved PRD/blueprint is ordinary implementation detail versus when it requires amendment or re-scope review.

The purpose is to preserve delivery flow for small, low-risk changes while preventing material changes from bypassing scope, customer alignment, engineering review, and release governance.

Change Trigger Rules

Change Type Ordinary Implementation Detail? Notes
Text changes directly on a page Yes Ordinary if the change does not alter workflow, behavior, commitments, or meaning in a way that changes acceptance.
Text changes driven out of a database Yes Ordinary if the data change does not require schema or code changes.
Addition of a hyperlink to an existing target Yes Ordinary when linking to an already-approved destination.
Change to a row in a database that does not involve a schema change or code change Yes Ordinary data/content maintenance.
Changes to rows in databases that require an EF migration No Requires amendment/re-scope review because it changes schema or code.
Changes to logical flow of the application No Requires amendment/re-scope review because it changes behavior or workflow.
Creation of new assets No Requires amendment/re-scope review because the asset did not exist in the approved scope.
Upload of graphic resources Yes Ordinary only when replacing or adding content within an already-approved design/location. Not ordinary if it changes UX, layout, brand direction, or creates a new asset concept.

Trigger Authority

Anyone may raise a concern that a proposed change is not ordinary and should trigger amendment/re-scope review.

Engineering owns the final decision because Engineering owns the understanding of implementation effort, technical impact, dependencies, risk, and delivery implications.

Before Engineering finalizes the decision, Product, Support, QA, DevOps, Security, the Customer, or other stakeholders may make their case and provide context. Once Engineering finalizes the decision, the decision is immutable for that change.

Work Continuation Rule

When Engineering decides a change requires amendment/re-scope review, unaffected work may continue.

Affected work is decided case by case. The default preference is to continue moving forward in the interest of time where doing so is reasonable, low-risk, and unlikely to create waste or rework. Engineering owns the decision about whether affected work should continue, pause, split, or wait for amendment approval.

Amendment Write-Up Ownership

When amendment/re-scope review is required, Product generally writes the amendment description and final impact summary.

Ownership split:

Area Owner
Amendment description Product
Customer/business impact Product
Technical impact Engineering
Final write-up drafting Product
Quality acceptance of the final write-up Engineering

Product owns writing the amendment clearly. Engineering owns deciding whether the write-up is high enough quality to work from.

Amendment vs New Request

The distinction between amendment and new request is often a judgment call. The process should provide guardrails, but it should not pretend every case can be qualified or quantified in advance.

Clear new request cases:

  • The change refutes the original understanding of the work.
  • The change is unrelated to the initial request.
  • The change changes the intended business outcome rather than adjusting how to reach it.
  • The change introduces a materially different capability, workflow, audience, or system behavior.

Clear amendment cases:

  • The change is a course correction to the approved work.
  • The change clarifies or adjusts the path to the same intended outcome.
  • The change remains connected to the same customer/business need.
  • The change can reasonably be understood as revising the current blueprint rather than starting a separate body of work.

Judgment principle:

We will often know it when we see it.

When the distinction is ambiguous, Engineering owns the final determination after hearing the case from Product, Support, QA, DevOps, Security, the Customer, or other relevant stakeholders.

Amendment Recording Rules

When an amendment is accepted, it should result in a related, linked ticket.

The parent ticket should receive a clear call-out that a new requirement or amendment exists. The call-out should link to the related amendment ticket and make the relationship visible to Product, Support, Engineering, QA, DevOps, and leadership reviewers.

The original user story, requirement, PRD section, or approved scope statement should not be silently modified in place. It should remain historically intact so reviewers can see what was originally approved and what changed later.

Recommended pattern:

  1. Create a related amendment ticket.
  2. Link the amendment ticket to the parent ticket.
  3. Add a parent-ticket call-out that a new requirement/amendment exists.
  4. Keep the original requirement unchanged.
  5. Put the new or changed requirement in the amendment ticket.
  6. Reference both the original requirement and the amendment during implementation, testing, and release review.

Fast-Track Approval

An amendment ticket does not require the same level of artifacts as the original PRD/blueprint.

Accepted amendments should use a fast-track approval between Product leadership and Engineering leadership.

Minimum approval record:

  • Amendment ticket link
  • Parent ticket link
  • Short amendment description
  • Customer/business impact
  • Technical impact
  • Product leadership approval
  • Engineering leadership approval
  • Engineering acceptance that the amendment is high enough quality to work from

The approval should be noted clearly in the amendment ticket and referenced from the parent ticket.

Release Scope Rule

If a change is accepted as an amendment, it becomes part of the release scope for the parent work.

An incomplete accepted amendment should be treated as part of the release decision. It may cause the release to hold, revise, re-scope, or split, depending on Engineering leadership and Product leadership review.

If the change is treated as a backlogged item, follow-on item, or new request, it does not block the current release.

Review and Validation Ownership

For review and release purposes, the complete requirement is the original requirement plus all accepted amendments.

Amendments do not create a separate validation owner by default. Responsibility stays with whoever would perform the same validation in the absence of amendments.

Examples:

  • Engineering remains responsible for implementation and PR review.
  • QA remains responsible for testing review.
  • Product remains responsible for acceptance validation.
  • DevOps remains responsible for packaging/deployment review where applicable.
  • Engineering leadership remains responsible for final ship/hold decision.

Customer Communication

Customer-facing communication for accepted amendments follows the normal Product/Support ownership flow.

Amendments do not create a special Engineering-to-customer communication path.
