Codex Operationalization Plan

This artifact defines how Agile Blueprinting and Blueprint to Release should become simple, guided Codex skills and plugins.

The goal is to remove process interpretation from the user. A user should not need to know what it means to create a PRD, initialize a delivery run, produce agent artifacts, or generate a SPOG. They should invoke the appropriate Codex workflow, answer guided questions, and receive the expected artifact output.

Product Principle

Codex operationalization should make the methodology feel easy.

The process may be deep under the hood, but the user experience should be guided, plain-language, and outcome-oriented. The user should not need to copy prompts, remember artifact contracts, know the full Blueprint to Release flow, or decide which template applies.

Initial Skill / Plugin Concept

Plugin Architecture

The working model is plugin plus skills.

A plugin is the team-facing bundle. A skill is the individual guided workflow inside that bundle.

Initial plugin bundles:

  • Operations plugin: skills used by Support/Ops and operational teams.
  • Product plugin: skills used by Product, Design, and BA-style discovery/blueprint work.
  • Engineering plugin: skills used by Engineering, DevOps, QA, Security, and release execution.

The bundles may become more granular later, but this is the initial organizing model. Users should be able to find workflows based on the team role they are operating in, not by memorizing the full methodology.

Skill Naming Convention

Skill names should be short, descriptive, and usable inside their plugin bundle.

The plugin provides the team context:

  • Operations plugin
  • Product plugin
  • Engineering plugin

The skill name should not need to repeat the plugin name, but it should be descriptive enough to remain clear if a user has more than one plugin installed.

Preferred MVP skill names:

  • prd-generator
  • prd-readiness-review
  • implementation-agent
  • unit-test-agent
  • e2e-test-agent

Avoid overly generic names such as generate, review, test, or run, because those become ambiguous when multiple plugins are installed.

PRD Generator

Working name:

  • prd-generator

Purpose:

  • Guide a user through creating a PRD/blueprint.
  • Ask questions in a sequence that helps the user clarify the desired outcome, workflow, requirements, acceptance criteria, risks, assumptions, and open questions.
  • Generate the best available PRD artifact from the answers provided.
  • Allow some questions to remain unanswered when necessary, while clearly marking open questions or assumptions.
  • Reduce the cognitive burden of "what does it mean to create a PRD?"

Expected behavior:

  1. User invokes the skill/plugin.
  2. Codex asks guided questions.
  3. Codex generates the PRD/blueprint artifact.
  4. Codex identifies unanswered questions, assumptions, and readiness gaps.
  5. Codex indicates whether the PRD appears ready for review or needs more discovery.

Candidate Workflow Surface

The operating model may need multiple skills/plugins across the full delivery gamut, including:

  • PRD/blueprint generation
  • PRD readiness scoring
  • Run initialization
  • Agent artifact generation
  • Artifact review
  • SPOG generation
  • HITL review capture
  • Amendment/re-scope review
  • Release readiness review

Session State and Knowledge Persistence

Guided workflow state should be persisted the same way this ideation workspace works:

  • Emerging concepts, incomplete decisions, and draft thinking are written as ideas or notes.
  • As ideas become fully baked, they are promoted into artifacts.
  • Artifacts become the source of truth for repeatable workflows.
  • Skills should read the relevant artifacts before acting so each session starts from persisted knowledge instead of relying on chat memory.

For operational skill runs, each active workflow should also maintain a small run/status record so Codex can resume without rediscovering everything from scratch.

Recommended state pattern:

<topic>/
  ideas/                         # still-forming concepts
  artifacts/                     # approved or mature process artifacts
  artifacts/<work-item-id>/      # run-specific delivery artifacts, when applicable
    00-run-metadata.md
    workflow-state.md            # current step, answered questions, open questions, next action

The workflow state file should not replace the artifact. It is a resume aid. The final artifact remains the durable output.

Frontmatter and Structured Data

Every artifact should eventually have YAML frontmatter for discoverability, ownership, status, and lifecycle management.

The depth of frontmatter should depend on how the artifact is used:

  • All artifacts get minimal frontmatter.
  • MVP skill-generated artifacts get richer frontmatter now because they need to support repeatable workflows.
  • Other artifacts get placeholder format decisions for now and should be revisited later.
  • Add separate JSON only when another tool or automation needs stable machine-readable detail beyond what YAML frontmatter can reasonably hold.
