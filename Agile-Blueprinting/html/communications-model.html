Communications Model

This document defines the communications model for Agile Blueprinting and Blueprint to Release across the three IT pillars:

  • Support / Operations
  • Product / Design
  • Engineering

Base Rule: No Ticket, No Work

If a customer wants to engage IT, the request must become a Jira ticket.

Customers can email, message, or discuss ideas informally, but until the request exists as a Jira ticket, it is not part of the official workflow.

No ticket, no work. Until it is a ticket, it is a dream.

System of Record

Jira is the common ticketing system for all three pillars.

Tickets can enter through Support/Ops or Product/Design. The entry point does not determine permanent ownership. Ownership is determined by categorization.

Categorization, Not Classification

Use the word categorized, not classified.

Classified has a different meaning in this environment and should not be used for ticket routing/status language.

Three-Pillar Model

Pillar Primary Role Customer Comms Production Change Authority
Support / Operations Triage, O&M, defects, operational support Owns comms for support/O&M/defect tickets Can use approved support/O&M tools
Product / Design Discovery, low-fi design, PRD/blueprint, feature ownership Owns comms for product/new request tickets No production implementation authority
Engineering Implementation, tests, PR review, packaging, release Never communicates directly with customers Owns implementation and release work

Security currently lives as a peer group under Ops. That may change, but the communications model should still treat security review as a required governance path when applicable.

Ticket Ownership Rules

Support-Owned Work

Support owns communication when the ticket should be in the Support/Ops lane:

  • Defect
  • O&M
  • Operational task
  • Support-resolvable issue

If Support can fix the issue using approved tools, Support should fix it. Support must communicate what it did to Product and Engineering as appropriate.

If the issue requires Engineering, Support creates a new blocking Engineering ticket and maintains customer-facing communication ownership unless ownership is formally transferred.

Product-Owned Work

Product owns communication when the ticket should be in the Product/Design lane:

  • New feature
  • New application
  • New workflow
  • Planned sprint work
  • Meaningful enhancement

Product performs discovery and low-fidelity design work. Product may use Figma or equivalent design tools, but only for low-fi exploration and customer alignment. Product should not prototype production solutions or drift into Engineering's lane.

Product does not implement production changes.

Product transfers implementation work to Engineering and owns pre-release and post-release customer communications for work in its lane.

Engineering-Owned Work

Engineering owns implementation and delivery quality:

  • Code implementation
  • Unit tests
  • Integration tests
  • End-to-end tests
  • PR review
  • Packaging
  • Release
  • DevOps work

Engineering owns communication back to Product and/or Support. Engineering does not communicate directly with customers.

Engineering must keep the owning customer-facing pillar informed, especially for blockers, clarifications, dev-complete handoffs, release readiness, and issues that affect expectations.

Red Line: Engineering Never Talks Directly to Customers

Engineering should never be in the room with customers.

Customer communication flows through Product or Support/Ops, depending on ticket ownership and category.

Rationale:

  • Prevents uncontrolled scope commitments.
  • Keeps customer-facing communication consistent.
  • Protects Engineering from ad hoc requirement negotiation.
  • Keeps Product and Support accountable for their lanes.
  • Avoids confusing technical discussion with customer commitment.

Transfer Rules

Ownership should follow the nature of the ticket.

Starting Pillar If Ticket Is Actually... Action
Support New feature, new app, enhancement, sprint/planned work Transfer to Product
Product Defect, O&M, support issue, operational task Transfer to Support
Support or Product Requires implementation Create/transfer/block Engineering ticket
Engineering Needs customer clarification Ask Product/Support to obtain clarification

State transfer requires explicit internal communication. The receiving pillar should not discover ownership changes passively.

Three Amigos Categorization

Ticket categorization should happen in a Three Amigos meeting with representation from:

  • Support / Operations
  • Product / Design
  • Engineering

Purpose:

  • Categorize the ticket.
  • Decide whether the juice is worth the squeeze.
  • Select the delivery lane.
  • Identify the owning customer-facing pillar.
  • Identify whether Engineering work is required.
  • Identify required HITL tollgates.
  • Identify communications expectations.

Possible ticket categories:

  • Defect
  • O&M / operational task
  • New request / feature / application
  • Amendment / re-scope
  • Security / risk

Delivery Lane Customer-Facing Owner Engineering Comms Owner Notes
Kanban / O&M Support / Operations Engineering communicates to Support Used for defects, support issues, O&M
Sprint / Planned Delivery Product / Design Engineering communicates to Product Used for new requests, features, new apps

Customer Communication Triggers

The owning customer-facing pillar should communicate at these moments:

  • Ticket received / acknowledged
  • Ticket categorized
  • Discovery scheduled
  • PRD/blueprint ready for review
  • Customer/proxy sign-off requested
  • Build started
  • UAT requested
  • Review ready
  • 48-hour release heads-up
  • Release completed
  • Ticket closure or acceptance requested
  • Follow-up/amendment needed

Internal Communication Triggers

Internal communication is required at these moments:

  • Ticket ownership transfer
  • Ticket categorized in Three Amigos
  • Engineering ticket created or linked as blocking work
  • Clarification needed
  • Blocker identified
  • Scope/risk issue discovered
  • Development complete
  • QA work needed
  • QA complete
  • Security review needed or complete
  • Packaging/deployment ready
  • Release ready
  • Release completed
  • Post-release issue found

Development Complete Handoff

When Engineering marks development complete:

  • Engineering creates or transitions the appropriate QA ticket/work item.
  • Engineering adds a Jira comment tagging the person or group that most immediately owned the ticket before Engineering, such as Product, Support/Ops, or a named requester from those teams.
  • Engineering summarizes what was completed, what evidence exists, and what still needs review.

Update Cadence Contracts

The process should define standard update cadences by category and lane.

Examples:

  • Defects may require updates every defined number of minutes/hours.
  • Features may require updates every defined number of days.
  • Operational tasks may follow O&M cadence.
  • Security/risk items may require restricted and more frequent updates.

Do not define exact cadence values in this document yet.

Requesters may request a cadence override, such as more frequent updates or a specific format. Overrides are negotiation points, not automatic requirements.

Once an override is agreed to, Engineering must comply with that communication contract through the owning customer-facing pillar.

Cadence contracts are part of the broader SLA model and should not be fully defined here yet.

Engineering-to-Pillar Communication Contract

Engineering must communicate to Product and/or Support:

  • Status changes
  • Blockers
  • Clarifications needed
  • Test/review readiness
  • Release readiness
  • Risks or deviations from the PRD/ticket
  • Any agreed cadence update

Engineering does not communicate directly with customers. Product or Support translates Engineering updates into customer-facing communication.

Tool Boundaries

All pillars use Jira.

Some tools intentionally differ by pillar:

  • Figma is part of Product/Design's flow.
  • Figma is not part of Support/Ops flow.
  • Product uses low-fi design artifacts for discovery and alignment.
  • Product should not prototype production solutions.
  • Support should not design product solutions.
  • Engineering should not negotiate requirements directly with customers.

Ticket Closure and Definitions of Done

There are multiple definitions of done in Blueprint to Release. This is intentional.

Different teams can be done with their portion of the work before the overall request is truly done. A ticket should not be closed simply because one pillar has completed its handoff.

Engineering Done

Engineering Done means Engineering has completed the work it owns and has no reason to believe more Engineering work is required before handoff.

Engineering Done may include:

  • Implementation complete.
  • Required unit tests complete.
  • Required integration tests complete.
  • Required end-to-end tests complete, when applicable.
  • Pull request created and reviewed according to policy.
  • Required QA handoff created or triggered.
  • Required security/package/deployment evidence generated or linked.
  • Engineering notes added to Jira.
  • Product, Support/Ops, QA, or the next owning group tagged in Jira.
  • Known risks, assumptions, deviations, or follow-up items documented.

Engineering Done does not mean the customer ticket is closed.

Engineering Done means Engineering has completed its part and handed the work to the next owner in the chain.

Product Done

Product Done will be defined by Product/Design later.

Likely considerations:

  • Customer discovery complete.
  • PRD/blueprint complete.
  • Customer/proxy sign-off obtained.
  • Low-fi artifacts reviewed.
  • UAT or customer acceptance coordinated.
  • Pre-release and post-release communications completed.
  • Follow-on requests or amendments created when needed.

Support / Operations Done

Support/Ops Done will be defined by Support/Operations later.

Likely considerations:

  • Triage complete.
  • Customer updates complete.
  • Support-resolvable fix applied, if applicable.
  • Engineering escalation created, if needed.
  • Operational validation complete.
  • Customer-facing closure communication complete.
  • Knowledge base/support notes updated, if needed.

Done

Done is the overarching definition of done.

A request is Done only when the work has reached the target environment, all required HITL approvals have occurred, the owning customer-facing pillar agrees requirements have been met, and the ticket has the evidence needed for closure.

Done means:

  • The work is deployed or delivered to the intended target environment.
  • Required QA/testing evidence is complete.
  • Required security review is complete.
  • Required packaging/deployment evidence is complete, when applicable.
  • Required documentation/release notes are complete.
  • Required HITL tollgates are signed off.
  • Product or Support/Ops, depending on ownership, agrees the ticket outcome has been met.
  • Customer/proxy acceptance is recorded when required.
  • Open amendments or follow-on requests are separated from the closure decision.
  • Closure note and evidence are attached to Jira.

Done does not mean:

  • "It feels done."
  • "Engineering finished but it was not deployed."
  • "It passed one test but has not gone through the required tollgates."
  • "The implementation ticket is closed but the customer-facing outcome is unresolved."
  • "There are unresolved requirements hiding inside the original ticket."

Tickets do not close until they are Done.

Customer Non-Response Policy

When customer input, sign-off, UAT/acceptance, or closure confirmation is required, customer non-response holds the work.

Default rule:

  • Before PRD/sign-off: hold until the customer or approved customer proxy responds.
  • During UAT/acceptance: hold until the customer or approved customer proxy responds.
  • At ticket closure: hold closure until the customer or approved customer proxy responds.

The process should not move forward merely because the customer did not respond. If the customer has a required role in the workflow, the customer must do that job before the work advances.

Escalation may be used to obtain the needed response, but escalation does not by itself replace the required customer/proxy response unless a formally authorized proxy decision is made.

Closure Rules

  • Any ticket opened in support of an initiative should remain open until the initiative reaches final verification and acceptance.
  • Supporting tickets include QA tickets, Engineering tickets, Development tickets, DevOps tickets, Security tickets, Packaging/Deployment tickets, and any other linked work needed to deliver the initiative.
  • Supporting tickets may move into states such as pending deployment, pending validation, blocked, ready for review, or equivalent workflow states, but they should not be closed before final approval.
  • Closing a customer-facing ticket does not happen until all supporting tickets are verified, accepted, and ready for closure.
  • Closing a supporting ticket does not happen until the complete initiative is verified and accepted by the final approval owner.
  • Product-owned customer tickets close only when Product's definition of done and Done are met.
  • Support-owned customer tickets close only when Support/Ops' definition of done and Done are met.
  • Material changes discovered near closure become amendments or follow-on requests, not silent scope drift.
  • If the customer does not respond to an acceptance or closure request, the owning pillar holds the work and escalates as needed to obtain the required customer/proxy response.
  • Every closure requires a closure note.
  • Every closure requires evidence links or attachments.

Final Approval Owner

Final approval for initiative closure comes from whoever made the request.

Rules:

  • If the customer made the request, the customer is the final approval owner.
  • If Product is proxying on behalf of the customer, Product still needs customer approval unless Product has been formally authorized as the customer proxy for that decision.
  • If Product created the request for Product's own need, Product is the final approval owner.
  • If Support/Ops created the request for an operational need, Support/Ops is the final approval owner.
  • Engineering does not become the final approval owner merely because Engineering delivered the implementation.

Closure Evidence

Closure evidence should not be overly prescriptive at this stage.

The core closure evidence is confirmation from the requester or final approval owner that what was delivered is what they expected to be delivered.

Supporting evidence should be linked or attached as needed, but the process should not require a heavy universal checklist before the teams have validated what evidence is truly useful.

At minimum, the closure record should make clear:

  • What was delivered.
  • Who confirmed it matched expectations.
  • When that confirmation occurred.
  • Any known limitations, amendments, or follow-on requests that affect closure.
