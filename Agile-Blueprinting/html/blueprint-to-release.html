Blueprint to Release

Blueprint to Release is the operating flow for Agile Blueprinting. It moves work from classified customer or business need to governed AI-assisted delivery, human review, release, and feedback.

This document intentionally excludes communications planning for now. Communications will be defined separately and then linked back into the process.

Core Flow

Intake
  -> HITL Classification Tollgate
  -> Delivery Lane Selection
  -> Discovery
  -> Blueprint / PRD Creation
  -> Definition of Ready
  -> Agent Planning
  -> Agent Execution
  -> Pull Request and Evidence Package
  -> HITL Review
  -> Release Decision
  -> Release
  -> Feedback / Amendment Loop

Stage 1: Intake

Purpose: Capture the request clearly enough for humans to classify it.

Inputs:

  • Customer request
  • Internal business request
  • Defect report
  • Support ticket
  • Operational request
  • Security/risk finding

Outputs:

  • Intake record
  • Initial requester
  • Affected customer/user group
  • Problem statement
  • Urgency signal
  • Known evidence, screenshots, logs, examples, or reproduction steps

HITL decision:

  • Is the request understandable enough to classify?
  • If not, return to requester for clarification.

Stage 2: HITL Classification Tollgate

Purpose: Decide what type of work this is before choosing the delivery lane.

Classification options:

Classification Description Typical Lane
Defect Expected behavior is broken or regressed Kanban / O&M
New request New capability, enhancement, or workflow Sprint / planned delivery
Amendment Change to an approved blueprint or in-flight deliverable Amendment / re-scope
Operational task Configuration, deployment, data, support, or maintenance work Kanban / O&M
Security/risk issue Vulnerability, compliance, access, data, or risk item Expedited / security-led

Required human decision:

  • Classification
  • Priority
  • Delivery lane
  • Required reviewers
  • Whether a full PRD is required or a lighter blueprint is sufficient

Exit criteria:

  • Work type is classified.
  • Delivery lane is selected.
  • Required governance path is known.

Stage 3: Delivery Lane Selection

Purpose: Route work into the right operating mode.

Sprint / Planned Delivery

Use when:

  • Work is a new request or meaningful enhancement.
  • Customer discovery is needed.
  • Scope and acceptance need to be agreed up front.
  • Release can be planned into a time box.

Expected artifacts:

  • Discovery notes
  • PRD / blueprint
  • Readiness rubric
  • Agent handoff plan
  • Pull request and evidence package

Kanban / O&M

Use when:

  • Work is a defect, support item, operational task, or maintenance request.
  • Flow-based handling is more appropriate than sprint planning.
  • The request may need rapid triage and turnaround.

Expected artifacts:

  • Intake/ticket record
  • Reproduction or operational evidence
  • Lightweight blueprint or fix note
  • Test evidence
  • Pull request and evidence package, if code/config changes are made

Expedited / Security-Led

Use when:

  • The work involves security, compliance, data exposure, access control, or urgent production risk.
  • Normal sequencing may need to be compressed.
  • Security or risk owner needs authority in the flow.

Expected artifacts:

  • Risk/security finding
  • Mitigation plan
  • Test/security evidence
  • Approval record
  • Pull request and evidence package

Amendment / Re-Scope

Use when:

  • A signed-off blueprint changes materially.
  • A customer or stakeholder changes the intended deliverable.
  • A discovered issue affects scope, workflow, data, rules, or acceptance.

Expected artifacts:

  • Amendment note
  • Impact assessment
  • Updated PRD or follow-on blueprint
  • Revised readiness decision

Stage 4: Discovery

Purpose: Ensure the Product Manager or Business Analyst has done the homework before the PRD is treated as ready.

Activities:

  • Meet with customer or customer proxy.
  • Understand the customer need and business outcome.
  • Walk the workflow end to end.
  • Review low-fidelity mockups, wireframes, workflow diagrams, or equivalent aids when helpful.
  • Identify contingencies, alternate paths, and exceptions.
  • Identify data, rules, validations, integrations, and permissions.
  • Capture in-scope and out-of-scope boundaries.

Outputs:

  • Discovery notes
  • Workflow notes or diagram
  • Mockups/wireframes, if applicable
  • Initial assumptions
  • Known risks

HITL decision:

  • Has enough homework been done to generate a PRD?
  • If not, return to customer discovery.

Stage 5: Blueprint / PRD Creation

Purpose: Generate the full blueprint for the requested deliverable.

Activities:

  • Run the LLM-driven PRD interview.
  • Generate the PRD.
  • Generate supporting outputs:
    • Executive summary
    • Engineering implementation brief
    • Agent handoff plan
    • QA and acceptance test brief
    • Security review brief
    • Packaging and deployment brief
    • Customer-facing summary
    • Assumptions
    • Open questions
    • Risk register
    • Readiness rubric

Primary artifact:

  • PRD / blueprint

HITL decision:

  • Is the PRD coherent enough for readiness review?
  • If not, revise the PRD or return to discovery.

Stage 6: Definition of Ready

Purpose: Confirm that the PRD is strong enough to govern agentic delivery.

Ready means:

  • Product/BA owner has done the homework.
  • Customer or proxy has been engaged.
  • Workflow and intended deliverable are clear.
  • Scope boundaries are explicit.
  • Major data, rules, validations, integrations, permissions, and acceptance criteria are documented or marked as assumptions.
  • Out-of-scope items are explicit.
  • The owner signs off that the PRD represents what the customer is asking to receive.

Readiness is not an estimation ritual. It is a quality and governance gate.

Outputs:

  • Approved PRD or revision request
  • Readiness rubric
  • Sign-off record
  • Amendment policy acknowledged

HITL decision:

  • Ready for agent handoff?
  • Needs revision?
  • Needs customer clarification?
  • Should be reclassified?

Stage 7: Agent Planning

Purpose: Convert the approved PRD into agent missions and rules.

Activities:

  • Define which agents are required.
  • Define inputs and expected outputs per agent.
  • Define rules each agent must follow.
  • Define evidence required for human review.
  • Define pull request expectations.
  • Define escalation conditions.

Standard agents:

  • Implementation agent
  • Quality/testing agent
  • Security agent
  • Documentation/comms agent
  • Packaging agent
  • Deployment/Helm agent
  • Artifact review agent

Outputs:

  • Agent handoff plan
  • Agent rules
  • Required evidence checklist
  • Review ownership matrix

HITL decision:

  • Are the agent missions and rules clear enough to execute?
  • If not, revise the handoff plan before build begins.

Stage 8: Agent Execution

Purpose: Have specialist agents produce work products and evidence.

Agent outputs:

Agent Work Product Evidence / Documentation
Implementation Code changes, branch, pull request draft Implementation notes, changed files, design decisions
Quality / Test Automated tests, test execution Test plan, test results, failures, coverage notes
Security Security checks and mitigations Security report, risks, remediation notes
Documentation / Comms Release notes, support docs, customer-facing drafts Documentation package and audience map
Packaging Docker/package assets Packaging manifest, build notes, runtime assumptions
Deployment / Helm Helm charts/deployment config Deployment notes, env/secrets checklist, rollback notes
Artifact Review Consolidated review package Single pane of glass

Escalation triggers:

  • PRD contradiction
  • Missing rule needed for implementation
  • Security risk
  • Test failure that changes scope
  • Deployment blocker
  • Agent deviation from PRD
  • Material customer-impacting ambiguity

HITL decision:

  • Continue execution?
  • Pause for clarification?
  • Return to PRD amendment?
  • Reject agent output?

Stage 9: Pull Request and Evidence Package

Purpose: Package AI-generated work into a normal engineering review path.

Agents can:

  • Create a branch.
  • Commit changes.
  • Open a pull request.
  • Add implementation notes.
  • Attach generated evidence.
  • Respond to review comments with proposed fixes.

Agents cannot:

  • Approve their own pull request.
  • Merge without human approval.
  • Override required checks.
  • Declare customer acceptance.
  • Waive security, QA, or release gates.
  • Change governing rules without human approval.

Required PR contents:

  • PRD link
  • Summary of implementation
  • Changed files/components
  • Test evidence
  • Security evidence
  • Packaging/deployment evidence, if applicable
  • Known assumptions
  • Known deviations from PRD
  • Open questions
  • Human approvals required

HITL decision:

  • Is the PR complete enough to enter review?
  • If not, return to agents for missing evidence.

Stage 10: HITL Review

Purpose: Validate that all rules were followed and that generated evidence is sufficient.

Review surfaces:

  • Pull request
  • Single pane of glass
  • Test report
  • Security report
  • Packaging/deployment notes
  • Documentation package
  • PRD readiness record

Possible decisions:

  • Approve
  • Request changes
  • Reject
  • Hold for customer clarification
  • Return to agent execution
  • Amend PRD
  • Reclassify work

Required principle:

  • Humans define the rules.
  • Agents execute and produce evidence.
  • Humans validate that evidence and approve or reject.

Stage 11: Release Decision

Purpose: Decide whether the approved work should ship.

Inputs:

  • Approved pull request
  • Passing required checks
  • QA approval
  • Security approval
  • Packaging/deployment readiness
  • Known risks
  • Rollback plan, if applicable

Possible decisions:

  • Ship
  • Hold
  • Ship with accepted risk
  • Return for fixes
  • Split release
  • Convert remaining work to amendment/follow-on request

HITL decision:

  • Final ship/hold decision.

Stage 12: Release

Purpose: Deploy or deliver the approved change.

Activities:

  • Merge approved PR.
  • Build/package release artifact.
  • Deploy through approved path.
  • Confirm release health.
  • Confirm rollback path if needed.
  • Record release outcome.

Outputs:

  • Release artifact
  • Deployment record
  • Release status
  • Known issues

HITL decision:

  • Is release complete and stable?
  • If not, invoke rollback, hotfix, or follow-on process.

Stage 13: Feedback / Amendment Loop

Purpose: Capture learning and handle change without silent scope drift.

Activities:

  • Validate customer or user outcome.
  • Capture defects or follow-on needs.
  • Identify amendments to the original blueprint.
  • Decide whether feedback is a defect, new request, amendment, operational task, or security/risk item.
  • Route back through intake classification.

Outputs:

  • Feedback notes
  • Acceptance record
  • Amendment request, if needed
  • New intake record, if needed

HITL decision:

  • Accepted as delivered?
  • Needs amendment?
  • New request?
  • Defect?

Tollgate Summary

Tollgate Human Decision Possible Outcomes
Intake Classification What kind of work is this? Defect, new request, amendment, O&M, security/risk
Discovery Readiness Is there enough understanding to write a PRD? Continue, clarify, stop
PRD Review Is the blueprint coherent? Revise, approve for readiness review
Definition of Ready Is the PRD strong enough for agent handoff? Ready, revise, clarify, reclassify
Agent Planning Review Are agent missions/rules clear? Execute, revise handoff
Execution Escalation Did agents hit ambiguity or risk? Continue, pause, amend, reject output
PR Entry Review Is evidence complete enough for review? Enter review, return to agents
HITL Review Did the work meet the rules? Approve, request changes, reject, hold
Release Decision Should this ship? Ship, hold, accepted risk, split, fix
Feedback Classification What is the post-release feedback? Accept, defect, amendment, new request

Communications Placeholder

Communications are intentionally not defined in this version. A separate communications model should define:

  • Who gets notified by classification and lane
  • Customer vs internal communications
  • Release notes
  • Incident/defect communications
  • Review and sign-off communications
  • Post-release feedback communications
